# WeakRef и FinalizationRegistry

Обычная ссылка на объект — «сильная»: пока она существует, сборщик мусора не может освободить объект. `WeakRef` — это *слабая* ссылка: она позволяет добраться до объекта, но не мешает его удалить. `FinalizationRegistry` — способ получить уведомление, что объект уже собран. Оба инструмента появились в ES2021 и нужны редко: это низкоуровневая оптимизация памяти для кэшей и больших объектов, а не обычная часть прикладного кода.

Важное предупреждение сразу: момент сборки мусора непредсказуем и зависит от движка, настроек и нагрузки. Код, правильность которого держится на том, что объект «обязательно когда-нибудь будет собран», — плохой код. Поэтому в этом уроке почти все выводы — о том, как *безопасно* работать, когда объект может исчезнуть в любой момент между задачами.

## Сильные и слабые ссылки

Сборщик мусора освобождает объекты, до которых нельзя добраться от «корней» (глобальные переменные, текущий стек вызовов и т. п.) по цепочке сильных ссылок. Присваивание переменной, поле объекта, элемент массива, ключ и значение `Map` — всё это сильные ссылки.

```js
let user = { name: 'Аня' };
const list = [user];
user = null;
console.log(list[0].name); // Аня — объект жив, его держит массив
```

Слабая ссылка не учитывается при подсчёте достижимости: если других (сильных) путей к объекту нет, его могут собрать.

## WeakRef: создание и deref

```js
let big = { data: new Array(1000).fill(0) };
const ref = new WeakRef(big);

console.log(typeof ref);          // object
console.log(ref.deref() === big); // true
```

- `new WeakRef(target)` — `target` обязан быть объектом (или незарегистрированным символом); примитивы дают `TypeError`: `new WeakRef(42)` падает.
- `ref.deref()` возвращает цель либо `undefined`, если цель уже собрана.
- Других методов нет. Сама слабая ссылка — обычный объект, и её нужно где-то хранить.

Всегда проверяйте результат `deref()`:

```js
const target = ref.deref();
if (target !== undefined) {
  // работаем с target — теперь у нас сильная ссылка на него
} else {
  // объекта нет, его надо создать заново
}
```

Пока вы держите результат `deref()` в локальной переменной, это обычная сильная ссылка, и объект в безопасности.

## Гарантия внутри одной задачи

Спецификация делает важную оговорку: если объект был получен через `new WeakRef(obj)` или `deref()`, он **не будет собран до конца текущей «задачи»** (текущего синхронного прогона кода, пока не вернётся управление циклу событий). Поэтому внутри одного синхронного блока два вызова `deref()` подряд дадут один и тот же объект, даже если других ссылок уже нет.

```js
let obj = { id: 1 };
const ref = new WeakRef(obj);
obj = null;
console.log(ref.deref() !== undefined); // true — мы ещё в той же задаче
```

А вот после `await` или таймера гарантии нет: `ref.deref()` может вернуть `undefined`. Если запустить Node с флагом `--expose-gc` и вызвать `gc()` после ожидания, то объект из примера выше действительно исчезнет. Обычный `node` флага не включает, а в песочнице проверки задач `gc` недоступен — поэтому задачи урока не зависят от сборщика.

Практическое правило: не храните результат `deref()` дольше, чем нужно, и не рассчитывайте, что два вызова в разных задачах вернут одно и то же.

## Пример: кэш на слабых ссылках

Типичная задача — кэшировать дорогие объекты так, чтобы кэш сам не держал их в памяти навечно.

```js
const cache = new Map(); // ключ -> WeakRef

function getCached(key, create) {
  const hit = cache.get(key)?.deref();
  if (hit !== undefined) return hit;

  const value = create(key);
  cache.set(key, new WeakRef(value));
  return value;
}
```

Если на значение никто больше не ссылается, оно будет собрано, и следующий запрос создаст его заново. Но есть тонкость: в `Map` остаётся **ключ вместе с мёртвой `WeakRef`**. Слабая ссылка не освобождает саму себя, поэтому при большом числе уникальных ключей сама `Map` растёт. Нужна чистка: периодически проходить по записям и удалять те, у которых `deref() === undefined`, либо использовать реестр финализации.

Почему не `WeakMap`? Ключи `WeakMap` — объекты, и записи исчезают вместе с ключом. Но кэшу обычно нужны *строковые* ключи (идентификаторы, URL), а слабым должно быть именно значение — этого `WeakMap` не умеет.

## FinalizationRegistry: уведомление о сборке

```js
const registry = new FinalizationRegistry((heldValue) => {
  console.log('Собран объект с ключом', heldValue);
});

let resource = { name: 'tmp' };
registry.register(resource, 'tmp-key');
resource = null; // когда-нибудь после сборки коллбэк получит 'tmp-key'
```

- `register(target, heldValue[, unregisterToken])` — следить за объектом `target`. Когда он будет собран, **может быть** вызван коллбэк реестра с `heldValue`.
- `heldValue` хранится реестром (сильно!) до вызова. Поэтому он **не должен ссылаться на `target`**: иначе объект никогда не будет собран. Более того, `register(obj, obj)` сразу бросает `TypeError`.
- `unregister(token)` отменяет наблюдение: в качестве `token` передают объект (часто сам `target`), указанный третьим аргументом `register`. Возвращает `true`, если что-то было снято, и `false`, если нет.
- Примитив в качестве `target` — `TypeError`.

```js
const reg = new FinalizationRegistry(() => {});
const obj = {};
console.log(reg.register(obj, 'x', obj)); // undefined
console.log(reg.unregister(obj));         // true
console.log(reg.unregister(obj));         // false — уже снят
```

Что важно помнить:

1. Коллбэк вызывается **не гарантированно**: например, программа может завершиться раньше, чем произойдёт сборка.
2. Вызов происходит позже сборки, в отдельной задаче; точное время не определено.
3. Коллбэк получает только `heldValue`, а не сам объект — объекта уже нет.
4. Не стройте на финализации логику, влияющую на корректность. Очистка «обязательных» ресурсов (файлы, соединения) должна выполняться явно (`close()`, `try/finally`), финализация — только страховка и оптимизация.

## Связка: кэш с автоматической чисткой

```js
const cache = new Map();
const cleaner = new FinalizationRegistry((key) => {
  // удаляем запись, только если в ней по-прежнему мёртвая ссылка
  const ref = cache.get(key);
  if (ref && ref.deref() === undefined) cache.delete(key);
});

function put(key, value) {
  cache.set(key, new WeakRef(value));
  cleaner.register(value, key);
}
```

Проверка `ref.deref() === undefined` нужна, потому что за время между сборкой и вызовом коллбэка под тем же ключом могли записать новое значение — его удалять нельзя. Здесь `heldValue` — строковый ключ: он не ссылается на значение, утечки нет.

## Альтернативы

Прежде чем брать `WeakRef`, подумайте, не хватит ли:

- `WeakMap`/`WeakSet`, если нужно привязать данные к объекту (приватные поля, метки, мемоизация по объекту-ключу);
- явного жизненного цикла (`dispose`, `close`), если ресурс легко освободить вручную;
- ограниченного кэша (LRU) с предсказуемым размером.

Слабые ссылки делают поведение программы недетерминированным, а ошибки — трудновоспроизводимыми.

## Типичные ошибки

> [!WARNING]
>
> - Не проверять результат `deref()` на `undefined`.
> - Сохранять результат `deref()` в долгоживущей переменной и удивляться, что объект «не собирается».
> - Передавать в `heldValue` сам объект или замыкание, ссылающееся на него.
> - Надеяться, что коллбэк `FinalizationRegistry` вызовется обязательно и вовремя.
> - Забывать чистить `Map` с мёртвыми `WeakRef`.
> - Пытаться проверить поведение в тесте через ожидание сборки мусора: результат зависит от движка.

## Коротко

> [!TIP]
>
> - `WeakRef` не мешает сборке объекта; `deref()` возвращает объект или `undefined`.
> - Цель — только объект; внутри одной задачи объект гарантированно жив.
> - `FinalizationRegistry` сообщает о сборке, но без гарантий по времени и самому факту вызова.
> - `heldValue` не должен ссылаться на цель, а `register(x, x)` — `TypeError`.
> - Кэш из `Map` со `WeakRef` требует чистки мёртвых записей.
> - Используйте это только как оптимизацию; критичную очистку делайте явно.
