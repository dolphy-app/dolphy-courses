# Автоматическое тестирование

Запустить функцию в консоли и посмотреть на результат — нормальный способ проверить её один раз. Но код живёт долго: его правят, расширяют, переписывают. Автоматические тесты превращают проверку «на глаз» в программу, которую можно запустить за секунду в любой момент.

## Зачем нужны тесты

Вы пишете функцию `f`. Проверили `f(1)` — работает. Проверили `f(2)` — не работает, исправили. А `f(1)` после правки перепроверили? Скорее всего, нет, и она могла сломаться. Ручная проверка забывает старые сценарии, а вручную прогонять десятки случаев после каждой правки никто не будет.

Автотест — это отдельный код, который вызывает вашу функцию с разными аргументами и сравнивает результат с ожидаемым. Что это даёт:

- **Защита от регрессий.** Сломали старое поведение — тест упадёт сразу.
- **Смелый рефакторинг.** Если тесты зелёные, внутренности можно переписывать.
- **Документация.** Тесты показывают, как функцию предполагается использовать и как она ведёт себя на краях.
- **Хорошая архитектура.** Код, который трудно тестировать, обычно плохо спроектирован: слишком много зависимостей, скрытое состояние.

## Разработка через описание поведения (BDD)

Идея проста: сначала описываем, что должен делать код, потом пишем код. Описание поведения и есть тесты. Возьмём функцию `pow(x, n)` — возведение `x` в целую степень `n ≥ 0` (в языке есть оператор `**`, но пример нужен ради процесса).

Спецификация состоит из трёх основных блоков:

- `describe("название", () => { ... })` — группа: что именно описываем;
- `it("что делает", () => { ... })` — один сценарий, внутри — проверки;
- `assert.equal(actual, expected)` — сама проверка; при несовпадении она бросает исключение, и тест считается проваленным.

Такой синтаксис у фреймворков Mocha, Jest, Vitest и у встроенного в Node.js модуля `node:test`. Вот спецификация на `node:test`:

```js
import { describe, it } from "node:test";
import assert from "node:assert/strict";

function pow(x, n) {
  let result = 1;
  for (let i = 0; i < n; i++) result *= x;
  return result;
}

describe("pow", () => {
  it("возводит 2 в степень 3", () => {
    assert.equal(pow(2, 3), 8);
  });

  it("любое число в степени 0 даёт 1", () => {
    assert.equal(pow(5, 0), 1);
  });
});
```

Если `pow(2, 3)` вернёт `9`, тест упадёт с сообщением вида `Expected values to be strictly equal: 9 !== 8`, и вы сразу увидите, какой сценарий нарушен.

## Цикл разработки

1. Пишем минимальную спецификацию — один-два сценария.
2. Пишем простую реализацию (можно даже неверную), запускаем тесты — они показывают, что не так.
3. Дописываем реализацию, пока всё не станет зелёным.
4. Добавляем новые сценарии — особенно **граничные случаи**: `n = 0`, `n = 1`, ноль в основании, пустой массив, очень большое число. Реализация снова красная — чиним.
5. Повторяем, пока не окажется, что всё важное покрыто.

Если нашли баг в боевом коде, сначала напишите тест, воспроизводящий баг (он должен упасть), затем чините. Тест останется навсегда и не даст ошибке вернуться.

Тест сам тоже может быть неверным, поэтому он должен быть простым и очевидным. Хороший тест убивает не только тот баг, который вы имели в виду: он различает правильную и неправильную реализации. Например, проверка `pow(2, 2) === 4` пройдёт и у правильной функции, и у ошибочной `return x * n;`, ведь `2 * 2` тоже равно 4. Достаточно добавить `pow(2, 3)` — и ошибка вскроется:

```js
const buggy = (x, n) => x * n;
console.log(buggy(2, 2)); // 4 — совпало случайно
console.log(buggy(2, 3)); // 6 — ожидалось 8
```

## Один тест — одна мысль

Можно сложить несколько проверок в одну функцию `it`. Но тогда при провале первой остальные не выполнятся, а название теста не подскажет, что именно сломано. Лучше несколько небольших `it` с говорящими названиями: по списку упавших сразу видно, какие сценарии нарушены. Если же сценарий требует одинаковых подготовительных шагов, их выносят в хуки.

Тесты можно группировать вложенными `describe`: «pow» → «положительная степень» → отдельные `it`.

## Хуки

Хуки — функции, выполняющиеся автоматически вокруг тестов:

- `before` — один раз перед всеми тестами группы;
- `beforeEach` — перед **каждым** тестом;
- `afterEach` — после каждого теста;
- `after` — один раз после всех.

`beforeEach` нужен, чтобы каждый тест стартовал с чистого состояния, а не зависел от того, что сделал предыдущий. Зависимость тестов друг от друга — частая причина «плавающих» ошибок, когда тест проходит в одном порядке и падает в другом.

## Что принято проверять

- **Типичный случай** — основной сценарий из документации.
- **Границы** — нули, пустые значения, единица, последний элемент.
- **Некорректный ввод** — функция должна бросать понятную ошибку или возвращать оговорённое значение. Для проверки исключений есть `assert.throws(() => f(), RangeError)`.
- **Отсутствие побочных эффектов** — функция не меняет аргумент, если это не её задача.

Не нужно проверять каждую мелочь: ориентируйтесь на поведение, видимое снаружи, а не на то, как функция устроена внутри. Тесты, привязанные к реализации, ломаются при безобидном рефакторинге — и их перестают уважать.

## Типичные ошибки

> [!WARNING]
>
> - Тест без проверок (`assert`) проходит всегда и ничего не доказывает.
> - Ожидаемое значение вычисляется тем же кодом, который проверяется (`assert.equal(pow(2, 3), pow(2, 3))`).
> - Тесты зависят друг от друга или от порядка запуска.
> - Проверяются только «счастливые» случаи, а границы забыты.
> - Тест слишком длинный, и по названию непонятно, что он проверяет.

## В этом курсе

В заданиях на код вам доступны функции `test(name, fn)` и `assert` — те же идеи без `describe`: вы пишете функцию, а наш набор тестов вызывает её и сравнивает результат с ожидаемым. Если что-то не сошлось, в сообщении проверки будет подсказка. Полезно читать эти проверки — как и любая спецификация, они показывают требования к функции.

## Коротко

> [!TIP]
>
> - Автотесты — отдельный код, который вызывает функцию и сравнивает результат с ожидаемым; он ловит регрессии и служит документацией.
> - Спецификация строится из `describe` (группа), `it` (сценарий) и проверок `assert`.
> - Сначала описываем поведение, потом пишем и дорабатываем код; баг сначала воспроизводим тестом.
> - Один `it` — один сценарий; хуки `beforeEach`/`afterEach` дают чистое состояние каждому тесту.
> - Хороший тест различает верную и неверную реализации, включая граничные случаи.
