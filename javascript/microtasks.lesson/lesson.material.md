# Микрозадачи

Обработчики промисов всегда выполняются асинхронно, даже если промис уже готов. Но «асинхронно» не значит «когда-нибудь»: у этого есть строгие правила, определяющие порядок вывода в самых каверзных задачах. В этом уроке разберём очередь микрозадач, её отличие от очереди таймеров и научимся безошибочно предсказывать порядок выполнения.

## Синхронный код не прерывается

JavaScript выполняется в одном потоке: пока идёт синхронный код, ничто другое выполниться не может. Все асинхронные обработчики (колбэки таймеров, `then`) ждут, пока текущий код полностью завершится, и только потом получают управление.

```js
const p = new Promise((resolve) => {
  console.log('executor');
  resolve('v');
});
console.log('sync 1');
p.then((v) => console.log('then', v));
console.log('sync 2');
// executor
// sync 1
// sync 2
// then v
```

Даже у уже выполненного промиса `then` не сработает сразу: обработчик только ставится в очередь.

## Очередь микрозадач

Когда промис выполнен (или отклонён), его обработчики `then`/`catch`/`finally` помещаются в **очередь микрозадач** (microtask queue). Движок следует правилу:

1. выполнить текущую задачу (синхронный код) до конца;
2. выполнить **все** микрозадачи из очереди, включая те, что появятся по ходу дела;
3. только после этого переходить к следующей «большой» задаче (например, колбэку `setTimeout`).

Поэтому микрозадачи всегда обгоняют таймеры, даже с задержкой `0`:

```js
console.log('1: код');
setTimeout(() => console.log('4: таймер'), 0);
Promise.resolve().then(() => console.log('3: микрозадача'));
console.log('2: код');
// 1: код
// 2: код
// 3: микрозадача
// 4: таймер
```

Свою микрозадачу можно поставить явно вызовом `queueMicrotask(fn)`. Она встанет в ту же очередь, что и обработчики промисов, в порядке вызова:

```js
queueMicrotask(() => console.log('queueMicrotask'));
Promise.resolve().then(() => console.log('promise'));
console.log('sync');
// sync
// queueMicrotask
// promise
```

## Макрозадачи: таймеры

Колбэки `setTimeout` и `setInterval` выполняются как отдельные «большие» задачи (в Node.js они проходят через фазы цикла событий). Между двумя такими задачами движок обязательно «очищает» очередь микрозадач.

```js
setTimeout(() => console.log('timeout A'), 0);
setTimeout(() => {
  console.log('timeout B');
  Promise.resolve().then(() => console.log('micro in B'));
}, 0);
setTimeout(() => console.log('timeout C'), 0);
// timeout A
// timeout B
// micro in B
// timeout C
```

Микрозадача, поставленная внутри таймера B, выполнится сразу после него, раньше таймера C. В Node.js 11 и новее это поведение совпадает с браузерным, в более старых версиях оно отличалось.

## Порядок внутри очереди

Микрозадачи идут строго в порядке постановки. Но «постановка» происходит в момент, когда промис становится готов, а не когда написан код:

```js
const p = Promise.resolve();
p.then(() => console.log('then 1')).then(() => console.log('then 3'));
p.then(() => console.log('then 2')).then(() => console.log('then 4'));
// then 1
// then 2
// then 3
// then 4
```

Оба первых `then` повешены на готовый промис и встают в очередь сразу: порядок `1, 2`. Вторые `then` на цепочках встают в очередь только после выполнения первых, то есть уже после `then 2`. Поэтому цепочки «чередуются».

Разберём задачу посложнее:

```js
console.log(1);
setTimeout(() => console.log(2), 0);
Promise.resolve().then(() => console.log(3)).then(() => console.log(4));
queueMicrotask(() => console.log(5));
(async () => {
  console.log(6);
  await null;
  console.log(7);
})();
console.log(8);
// 1
// 6
// 8
// 3
// 5
// 7
// 4
// 2
```

Разбор. Сначала синхронно: `1`, затем тело async-функции до первого `await` (`6`), затем `8`. К этому моменту в очереди микрозадач: обработчик `3`, `5`, продолжение async-функции после `await` (`7`). Они выполняются по порядку: `3` (и тут же ставит в очередь `4`), `5`, `7`, потом `4`. Только когда очередь пуста, срабатывает таймер: `2`.

Правило для `await`: код после `await x` продолжается как обработчик `then`, то есть тоже микрозадача.

## Бесконечные микрозадачи

Раз очередь микрозадач очищается до конца, микрозадача, которая постоянно ставит новую микрозадачу, **заблокирует** выполнение таймеров и отрисовку (в браузере). Из-за этого «рекурсивная» микрозадача без условия остановки приводит к зависанию:

```js
let n = 0;
function loop() {
  if (++n < 5) queueMicrotask(loop);
  else console.log('цикл микрозадач завершён', n);
}
queueMicrotask(loop);
setTimeout(() => console.log('таймер'), 0);
// цикл микрозадач завершён 5
// таймер
```

Здесь цикл конечен, поэтому таймер всё-таки наступил позже. Без условия остановки он никогда бы не наступил.

## Необработанные отклонения и микрозадачи

Когда очередь микрозадач опустела, а у отклонённого промиса всё ещё нет обработчика, движок сообщает о необработанном отклонении. Поэтому подписка «позже» (например, из `setTimeout`) не успевает:

```js
process.on('unhandledRejection', (r) => console.log('unhandled:', r.message));

const p = Promise.reject(new Error('late'));
setTimeout(() => p.catch(() => console.log('поймали поздно')), 0);
// unhandled: late
// поймали поздно
```

В Node.js 15+ без `unhandledRejection`-обработчика процесс бы уже упал. Правило: вешайте обработчик ошибки в том же синхронном фрагменте кода, где создали промис, или хотя бы до конца текущей задачи.

## Практические выводы

- Код после `await` и обработчики `then` всегда выполняются после текущего синхронного кода.
- Микрозадачи имеют приоритет над таймерами: `Promise.resolve().then(f)` сработает раньше `setTimeout(f, 0)`.
- `queueMicrotask(fn)` — способ выполнить функцию «как можно скорее, но асинхронно». Он нужен, чтобы сделать API единообразным (например, чтобы колбэк всегда вызывался асинхронно).
- Тяжёлые вычисления в микрозадачах блокируют цикл событий так же, как и в обычном коде; их можно разбивать через `setTimeout`.

## Типичные ошибки

- Думать, что `setTimeout(f, 0)` выполнится «сразу»: он ждёт и конца синхронного кода, и очереди микрозадач.
- Считать, что цепочки двух промисов выполняются «по одной»: их шаги чередуются, если стартуют вместе.
- Забыть, что код после `await` — тоже микрозадача, а не продолжение синхронного потока.
- Запускать бесконечный цикл на `queueMicrotask`: страница или процесс зависнут.
- Подписываться на отклонённый промис «позже» и ловить `unhandledRejection`.

## Коротко

- Обработчики промисов и `await` выполняются через очередь микрозадач.
- После завершения синхронного кода сначала выполняются **все** микрозадачи, и только потом — следующая макрозадача (таймер).
- Порядок в очереди — порядок постановки; шаги разных цепочек чередуются.
- `queueMicrotask(fn)` добавляет функцию в ту же очередь.
- Бесконечно самовоспроизводящиеся микрозадачи блокируют таймеры.
