# Ниндзя-код: чего избегать

Эта тема построена на иронии: вместо списка правил «как писать хорошо» мы разберём приёмы, которыми можно сделать код максимально непонятным. Зачем? Чтобы научиться узнавать их в чужом коде (и в своём, написанном в спешке) и не повторять. Каждый «совет ниндзя» ниже — это антипаттерн, а настоящий совет — делать наоборот.

Код читают гораздо чаще, чем пишут. Чтобы понять чужую строку, человек тратит минуты, а то и часы, и каждая загадка умножается на число читателей. Поэтому «написать короче» почти никогда не стоит потери понятности.

## Краткость любой ценой

Самый популярный способ запутать читателя — сжать логику в одну строку, используя возможности языка неочевидным образом. Вложенные тернарные операторы — классика:

```js
function normalize(i, len) {
  return i ? i < 0 ? Math.max(0, len + i) : i : 0;
}

console.log(normalize(-2, 5)); // 3
console.log(normalize(2, 5));  // 2
console.log(normalize(-9, 5)); // 0
console.log(normalize(0, 5));  // 0
```

Чтобы понять, что здесь происходит, придётся разбирать приоритеты операторов и вспоминать, какая именно ветка относится к какому условию. Та же логика, записанная прозрачно:

```js
function normalizeIndex(index, length) {
  if (!index) return 0;               // 0, NaN, undefined → начало
  if (index < 0) return Math.max(0, length + index); // отсчёт с конца
  return index;
}

console.log(normalizeIndex(-2, 5)); // 3
```

Строк больше, а читать быстрее: каждая ветка получила своё место и, при желании, комментарий. Размер исходника не влияет на скорость программы — минификатор позже сожмёт всё сам.

## Имена переменных и функций

Имена — главный носитель смысла в коде. Ниндзя это знает и атакует с нескольких сторон.

**Однобуквенные имена.** `a`, `b`, `c` невозможно найти поиском по файлу и невозможно расшифровать. Исключение — общепринятые соглашения, например счётчик цикла `i`, `j`. А вот если в двух страницах тела цикла счётчик назван `x`, читатель не поймёт, что это индекс, пока не пролистает вверх.

**Сокращения.** `lst` вместо `list`, `brsr` вместо `browser`. Угадать такое может только автор, и то неделю спустя.

**Слишком абстрактные имена.** `data`, `value`, `item`, `obj`, `info`, `result` подходят чему угодно, а значит, ничего не говорят. Имя должно отвечать на вопрос «что это?»: `userList`, `discountPercent`, `selectedRow`.

**Похожие имена.** Две переменные `data` и `date`, `userName` и `username` в одной области видимости — гарантированная путаница. Особенно коварны имена, различающиеся только регистром или одной буквой.

**Имена, которые лгут.** Функция `isReady()`, которая заодно запускает загрузку, или `getUser()`, которая удаляет запись из кэша. Имя обещает одно, код делает другое. Правило простое: префиксы `get…`, `is…`, `has…` — для чтения, и никаких побочных эффектов. Для действий — глаголы: `loadUser`, `saveForm`, `removeFromCache`.

**Повторное использование имён.** Если внутри функции вы объявили параметр с тем же именем, что и внешняя переменная, внешняя становится недоступной, и читатель не сразу поймёт, о какой из них речь:

```js
let value = 10;

function calc(value) {   // скрывает внешнюю value
  value = value * 2;
  return value;
}

console.log(calc(3), value); // 6 10
```

Ошибок в этом коде нет, но придётся помнить, какая `value` где. Лучше дать разные имена: `inputValue`, `doubled`.

## Побочные эффекты и неожиданные операции

Ниндзя любит выражения, которые делают сразу несколько вещей. Постфиксный и префиксный инкремент в одном выражении:

```js
let a = 1;
let r = a++ + ++a;
console.log(r, a); // 4 3
```

Первый `a++` возвращает 1 и увеличивает `a` до 2; `++a` увеличивает до 3 и возвращает 3; сумма — 4. Можно вычислить, но зачем заставлять читателя это делать? Вынесите шаги в отдельные строки.

Другая ловушка — функция, которая меняет аргумент, хотя по названию этого не ждёшь:

```js
function sorted(arr) {
  return arr.sort((x, y) => x - y); // sort меняет исходный массив!
}

const src = [3, 1, 2];
const res = sorted(src);
console.log(src); // [ 1, 2, 3 ] — оригинал изменился
console.log(res === src); // true
```

Если название обещает «отсортированную копию», она и должна быть копией: `[...arr].sort(...)`.

## Длинные функции и «умные» трюки

Функция на двести строк, которая и читает данные, и проверяет их, и рисует результат, — подарок для ниндзя. Разбивайте на небольшие функции с понятными именами: хорошая функция делает одно дело, и её название описывает это дело. Тогда часть комментариев становится не нужна: код сам объясняет, что происходит.

Ещё несколько приёмов, от которых стоит держаться подальше:

- **Нестандартные решения вместо общепринятых.** Если в команде принят единый стиль, не изобретайте свой: отступы, кавычки, порядок аргументов.
- **Хитрые обходы.** Побитовые операции вместо `Math.floor` (`~~x`, `x | 0`) работают не для всех чисел и сбивают читателя с толку.
- **Скрытые зависимости.** Функция берёт значения из глобальных переменных вместо параметров; без чтения всего файла непонятно, от чего зависит результат.
- **Глушение ошибок.** Пустой `catch {}` прячет проблему вместо того, чтобы дать её увидеть.
- **Магические числа.** `if (status === 3)` — что за тройка? Дайте константе имя: `STATUS_PAID`.
- **Комментарии, которые повторяют код или устарели.** `// увеличиваем i` над `i++` — шум, а комментарий, который противоречит коду, хуже его отсутствия.

## Как выглядит нормальный код

Хороший признак: код читается почти как текст. Имена говорят сами за себя, функции короткие, у каждой понятная ответственность, а комментарии объясняют *почему*, а не *что*. Прочитав функцию, вы можете в одном предложении сказать, что она делает.

Полезный ориентир — прийти к собственному коду через полгода и попробовать понять его без подсказок. Если не получилось, это сигнал к переделке.

## Типичные ошибки

> [!WARNING]
>
> - Считать, что короткий код — быстрый. Скорость определяется алгоритмом, а не количеством символов.
> - Оправдывать неясное имя тем, что «в контексте и так понятно». Через неделю контекст забудется.
> - Править «ниндзя-код» при случайной возможности без тестов. Сначала опишите поведение проверками, потом упрощайте.

## Коротко

> [!TIP]
>
> - Понятность важнее краткости: пишите прозрачно, пусть строк станет больше.
> - Имена должны говорить, что это; избегайте `data`, `obj`, сокращений и однобуквенных имён вне общепринятых счётчиков.
> - Имя функции не должно лгать: читающая функция не должна ничего менять.
> - Не прячьте несколько действий в одно выражение (`a++ + ++a`), не меняйте аргументы без необходимости.
> - Делите длинные функции на небольшие и называйте константы вместо «магических» чисел.
